# Lessons

One line per confirmed mistake: what went wrong, the rule now, and the test that guards it.

- **Read the vendor's API reference before coding an integration.** Didit's create-session reply puts the link in `url`, not `verification_url`, so valid sessions were treated as failures. Test mocks now copy the documented response. Guarded by `didit.test.ts`: "201 de Didit guarda session_id y url".
- **Don't trust a URL from an API or the database just because it's https.** Links are allowed only from `verify.didit.me`, and saved links are re-checked before they're returned. Guarded by `didit.test.ts`: "enlace de Didit" and "retomar".
- **Vendors may return an existing resource instead of creating one.** Didit returns the same open session for the same `vendor_data`, which broke our unique `session_id`. Migration 0019 links it to the attempt that already had it. Guarded by `95_identity_attach_tests.sql`.
- **Never delete a vendor resource you can't prove is yours.** Deletion needs a UUID, the same professional and workflow, "Not Started", and no other attempt using it. Guarded by `didit.test.ts`: "no se borra una sesión que…".
- **Log codes, not contents.** No vendor bodies, exception text, tokens, keys, user ids or document data in function logs. Every failure test asserts this.
- **A webhook header timestamp can be unsigned.** Check the signed body `timestamp` too, so an old signed body can't be replayed with a fresh header. Guarded by `didit.test.ts`: "un aviso firmado pero viejo no entra".
- **Webhooks can arrive before your own write.** Didit's "Not Started" can beat the session save, so retry, then return 500 so Didit retries. Guarded by `didit.test.ts`: "espera y reintenta".
- **A CI run that skips its tests must fail, not pass.** A missing secret is now a hard error in `didit-dev.yml`.
- **Diagnose secrets by name before changing code.** `SUPABASE_ANNON_KEY` (typo) looked like an empty `SUPABASE_ANON_KEY`. Workflows print only whether a secret is set and its length, never the value.
- **CI host checks scan comments too.** A `https://` link in a comment would have failed the "only Didit and the database" check. Write hosts in comments without the scheme.
- **Node's type stripping doesn't type-check.** `send-otp` passed its Node tests but failed `deno check` on a `Uint8Array` type. Bundled Edge Functions now always go through `deno check` before they're handed over for deploy.
- **Check the exact Edge Function name before testing a deploy.** Dev had `identity-check` and `Identity-check`; the new code went to the unused one. A failure reply without `reason`/`didit_status` means the old identity-check answered.
- **Sessions orphaned by old code come back.** Didit reuses an open session for the same `vendor_data`, so its "Not Started" webhook may never arrive again. The first sandbox run after a fix can miss that check; the next run starts clean.
- **Bienvenida: two crops of one photo are still the same picture.** Slides 2 and 4 used the same professional, so on the phone they looked identical. Each slide now has its own photo, and screenshots of all four are checked by eye before an APK. Guarded by `onboarding_layout_test.dart`: "cuatro fotos distintas" (catches repeated files, not repeated photos).
- **CI debug APKs are signed with a new key each run.** Android refuses to install one over another, so the phone can keep the old app. Uninstall before installing a new test APK, and check the build number in Perfil.
- **A new table must be added to `verify_remote.sql` too.** 0038 added `receiving_accounts`, the dev check expected 57 tables and failed after the migrations were already applied. `run_local.sh` now ends with the same check, so this fails locally first.
- **A cleanup function nobody schedules never runs.** `run_booking_housekeeping()` existed from 0007 but nothing called it, so unanswered requests stayed open and could be accepted late. 0046 guards the rule in the database itself (a trigger), closes overdue requests when the app opens, and schedules the job only where pg_cron exists. A scheduled request now also expires at its appointment time, not 12 hours later.
- **No migration without a checked backup.** Dev (Supabase Free) has no automatic backups. `respaldo-dev.yml` dumps, counts rows against the live database, test-restores and encrypts; `supabase-migrations.yml` won't apply anything unless that job succeeded in the same run.
- **Suspending someone must also stop what they already have open.** Suspension took a professional out of search and ¡Ya!, but their accepted bookings stayed live: they could still go "en camino" and see the address. 0047 cancels unstarted bookings on suspension (both sides), blocks non-approved professionals in the database, and hides addresses. Guarded by `99p_inactive_professional_tests.sql`.
- **A new column must also be in the app's `select`.** 0049 added `service_problems.opens_category_id`, the demo data had it, and every widget test passed, but `SupabaseBackend.problems()` listed its columns and left it out. On dev, "Grúa" in Mecánica was a plain option the server rejects. Found by the dev end-to-end test ("catálogo: … Grúa en Mecánica lleva al servicio de grúa"), which now guards it.
- **Supabase `.stream()` reads once, before its channel connects.** The live channel took more than 2 seconds on dev, and nothing reloaded once it was up, so a chat message sent in that window (even your own) only appeared after reopening the chat. `SupabaseBackend._liveRows` now reloads when the channel connects and keeps live updates that arrive during the reload. Guarded by the dev end-to-end test "tiempo real: el mensaje del profesional le llega al cliente al momento", which sends as the chat opens.
- **A test professional on dev must not look identity-checked.** Approving …02 with placeholder carnet photos would have stored them as genuine and shown "Verificado". 0061 adds `test_fixture` (only postgres can set it); marked profiles never show "Verificado", and `supabase/e2e/dev_fixture_pro.sql` approves or reverts …02 with labeled placeholder records while the carnet rule stays untouched. Don't run the dev end-to-end test while …02 is approved and available in Santa Cruz: its ¡Ya! requests would reach that phone.
- **The saved debug key is per branch and expires.** GitHub keeps an Actions cache only for the branch that made it, and drops it after 7 days unused. Build 15 (branch `builds/movil`) and builds 32–37 (`feature/base-app`) had different keys, so Samsung 2 couldn't update from 15; by the time we looked, the old key was gone and the phone had to be reinstalled. `mobile-builds.yml` now fails if the key isn't the one the test phones have (B5:2E:AE:FA…). Build test APKs only from `feature/base-app`.
- **Accepting without a price let the work start unpriced.** "Aceptar pedido ¡Ya!" confirmed jobs with no amount and "¿Cuánto cobraste?" was set by the professional alone. 0062 makes the database refuse any confirmation without a price both accepted (`HMY_PRICE_REQUIRED`), locks it (`HMY_PRICE_LOCKED`), and computes the final amount itself. Old SQL tests use `test.agree()` instead of `claim_ya_request`.
- **Firebase said "sent" but the phone showed nothing.** A push that arrives while the app is open goes to the app, not to Android's notification shade, and the app ignored it. Every "Enviar aviso de prueba" is pressed with the app open, so the test always looked broken (dev: HTTP 200 `sent:1` for both of 02's tests). The app now shows it itself on the "avisos" channel (`MainActivity.showNotification`). Test lock-screen delivery from the other phone, with this one locked.
- **"Verificado" meant only "approved".** Approval checks the carnet by hand; it isn't identity verification. 0063 shows "Identidad verificada" only with a real (non-sandbox) identity check, so on dev nobody has it while Didit is sandbox-only. Rankings (Plata, Oro, Diamante) are separate and never imply identity.
- **The public profile didn't send its service.** `get_professional_public` had the category name but not its id, so "Programar" from a profile opened the full category list. 0063 adds `primary_category_id`; the flow also lists only that professional's services and shows "Para: …".
- **Lists only refreshed from the live connection.** Android drops it while the phone is locked or the app is in the background, so a job confirmed in that time (F9A50778, Bs 120) was on dev but missing from 02's Activos until the list reloaded. `bookingChangesProvider` now also fires when the app returns to the foreground and when the live channel reconnects. `my_bookings` (0064) also always includes jobs in progress, even past its 100-row limit.
- **Never credit a wallet from the app.** QR recharges (0065) are credited only by `hmy_qr_settle`, which only the server can call with a provider notice it verified; amount, currency and expiry are checked and the credit happens once (ledger key `qr:<id>`). The dev mock (`dev_simulate_qr_payment`) works only for test profiles while `qr_recharge_provider` is `dev_mock`, and its credits are labeled "Recarga simulada (no es dinero real)".
- **A reservation is still money the professional can't see.** 0062 reserved the commission at agreement, so the wallet showed "reservado" and a lower "disponible", which confused professionals. 0066 (owner's final rules) reserves nothing: the commission is charged once, when the customer taps "Ya pagué", and agreeing a price only checks, with the wallet row locked, that the balance covers the commission of every agreed job not yet charged. Guarded by `99zb_commission_on_payment_tests.sql`, `concurrency/commission_race.sh` and `concurrency/payment_race.sh`.
- **An authorization error was really a UI bug.** In 69E3FD38 the professional had tapped "No puedo" nine seconds after the offer arrived, so the server correctly refused the later "Aceptar" with a generic `HMY_FORBIDDEN`, while the app still showed the buttons. 0067 returns `HMY_OFFER_DECLINED`/`HMY_REQUEST_EXPIRED`/`HMY_ALREADY_TAKEN`, the app shows "Rechazaste este pedido" with "Volver a tomar el pedido" (`reopen_ya_offer`), and "No puedo" asks first. Read `booking_offers`/`booking_events` before touching RLS.
- **"Monto aparte" added to the price; people typed the new total.** F3358CEF went from Bs 100 to Bs 230 because Bs 130 was added. 0067 replaces it with "Contraoferta": the amount is always the new total, the price changes only when the other side accepts, and a new proposal supersedes the open one. Guarded by `99zc_counteroffer_cancel_penalty_tests.sql` and `concurrency/counteroffer_cancel_race.sh`.
- **A wallet line must show the total change, not only "disponible".** F9A50778's commission capture moved only reserved money (0062 rules), so the history showed "—". `my_wallet_history` (0067) returns available + reserved deltas, the booking code and the balance after each row.
